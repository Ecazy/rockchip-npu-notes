# 同核 GEMM＋GEMV：链式编排与并发 job 能否隐藏计算

2026-10-14，Orange Pi 5 Plus / RK3588，内核 `6.1.43-rockchip-rk3588-rknpu098`，厂商 `rknpu 0.9.8`，NPU 1 GHz。
链式组固定在 Core 0；并发组用两个 barrier 同步的进程，提交线程 `taskset -c 4,5`（两个 A76）。
正式证据：[overlap-20261014-155212](custom-ops/results/2026-10-14/overlap-20261014-155212/)，
汇总见 [analysis.json](custom-ops/results/2026-10-14/overlap-20261014-155212/analysis.json)。
本轮是 [同核 MatMul/DPU 重叠实验](SAME-CORE-OVERLAP.md) 的扩展：保留原 MatMul＋LUT 组，新增 GEMV、放大组与跨核并发正对照。

## 结论

在当前厂商提交通路上，三种收益被分开了：

- **链式 Submit 只减少 Submit 开销，不隐藏计算。** 无论 `[GEMM, GEMV]`、`[GEMV, GEMM]`、
  `[GEMM, B8]`、`[GEMM, B16]` 还是同类的 `[GEMV, GEMV]`，链比两次独立提交少的都正好是**一次约 52 µs 的固定服务包络**；
  异质链相对同类链的额外节省只有 **−1 ns 到 876 ns**（两轮、n=64）。
- **当前驱动下同核两个并发 job 串行。** `P_same` 两个 job 都指定 Core 0，服务和/`T_pair` ≈ 0.95，两个完成中断都在 Core 0；计时与驱动单活动 job 机制一致。
- **跨核并发是真实的正对照。** `P_cross`（Core 0 / Core 1）测得 `T_pair` 明显小于服务和（1.31–1.32×），
  两个完成中断分别落在 Core 0 和 Core 1。测量方法能看见驱动服务包络重叠，尚未取得纯 MAC 执行时间线。
- 因此：链式编排在本实验里只买到约 12% 的 Submit 开销下降（2-task 链），买不到执行时间隐藏；
  跨核是本轮验证成功的服务重叠方式，不是链内收益；当前端到端墙钟尚未显示跨核加速，其他合并计算或减少传输的优化不在本轮排除范围内。

## 两个计算

| Task | 数学 | 逻辑 M/K/N | 物理 M | task | regcmd |
|---|---|---|---:|---:|---:|
| A：GEMM | `C = X × Wᵀ` | 256/256/256 | 256 | 1 | 126 word |
| B：GEMV | `y = x × Vᵀ` | 1/256/256 | **12** | 1 | 126 word |

GEMV 走已验收的逻辑 `M=1` 路径；框架把物理行补到至少 12，所以**这不是原生单行硬件执行**，
verify 记录里的 `physical_rows=12` 就是实际值。A、B 使用不同的输入、权重、输出 BO，构造/打包/上传都在计时之外。
每个 arm 提交前对参与的输出填 NaN 哨兵，提交后逐实例独立评分（mm tol 0.02，lut tol 0.002）并检查 BO guard。
B₈、B₁₆ 是 8 个、16 个独立 GEMV 组成的一个 Submit；它们只用于提高灵敏度，不替代单 GEMV 的结论。

本轮固定 K=N=256。`K=1024/4096` 需要 K 分片、会改变编排，未在本轮运行。

## 链式对照

两轮各 64 次采样、预热 8 次，arm 顺序逐轮轮换。中位服务包络（`hw_elapse_time`，纳秒），
`B8`/`B16` 的 task 数为 8/16，`C_AB8`/`C_AB16` 为 9/17：

| arm | run a 服务 | run b 服务 | 端到端墙钟 a（含下载/校验） |
|---|---:|---:|---:|
| A | 345,037 | 344,453 | 1,801,746 |
| B | 82,249 | 82,832 | 577,492 |
| B8 | 293,121 | 292,246 | 1,134,860 |
| B16 | 531,409 | 531,702 | 1,785,122 |
| `C_AB` | 375,078 | 374,350 | 1,891,870 |
| `C_BA` | 374,786 | 374,203 | 1,886,037 |
| `C_AB8` | 585,658 | 583,909 | 2,454,342 |
| `C_B8A` | 585,951 | 583,909 | 2,454,342 |
| `C_AB16` | 823,948 | 823,072 | 3,110,000 |
| `C_B16A` | 823,947 | 823,364 | 3,112,042 |
| `C_AA` | 636,700 | 635,533 | 3,126,041 |
| `C_BB` | 112,582 | 112,873 | 659,741 |

判定量按配对样本计算（`saving = sum − chain`，n=64）：

| run | `Δ_AB` | `Δ_AB8` | `Δ_AB16` | `Δ_BB` | `2·B8 − B16` |
|---|---:|---:|---:|---:|---:|
| a | 52,208 | 52,500 | 52,499 | 51,916 | 54,833 |
| b | 52,936 | 52,790 | 53,083 | 52,791 | 52,791 |

异质链相对同类对照 `Δ_BB` 的额外收益：

| run | `Δ_AB−Δ_BB` | `Δ_AB8−Δ_BB` | `Δ_AB16−Δ_BB` |
|---|---:|---:|---:|
| a | +292 | +584 | +583 |
| b | +145 | −1 | +292 |

全部落在噪声/包络量级（≤0.9 µs，约为包络的 1.7%），没有稳定、超出对照的额外收益。
`[GEMM, LUT]` 的回归组同样只省一次包络（`Δ_AB`=52,208，`Δ_BB`=52,354，差 −146 ns）。

包络模型也解释了放大组：`C_AB8 ≈ A + B8 − 52.5 µs`（345.0+293.1−52.5=585.6 µs），
`B8 ≈ 8 × (B − 包络) + 包络`（8×30+52≈292 µs）。

## 并发 job 对照

两个并发组用两个进程、各自一个 fd、各自独立的输入/权重/输出 BO，用管道 barrier 同时放行，
记录 `T_pair = max(done) − min(start)`（取两边的 `ioctl_begin`/`ioctl_end`）。

| run | arm | `T_pair` µs | 服务和 µs | 和/`T_pair` | 墙钟 µs | 完成中断 |
|---|---|---:|---:|---:|---:|---|
| a | `P_same` | 472.9 | 454.3 | 0.961 | 2281.8 | `[2,0,0]` |
| a | `P_cross` | 400.7 | 527.3 | **1.316** | 3109.1 | `[1,1,0]` |
| b | `P_same` | 432.8 | 409.6 | 0.946 | 2418.0 | `[2,0,0]` |
| b | `P_cross` | 398.6 | 522.2 | **1.310** | 3055.5 | `[1,1,0]` |

`P_same` 的 `T_pair` ≈ 服务和，结合驱动每核单活动 job 机制，支持同核两个 job 在队列里串行；`T_pair` 大于服务和的部分包含服务包络之外的 Host 开销及可能的提交/调度间隙，尚未细分。
`P_cross` 的 `T_pair` 比服务和短约 126 µs，且两核各有一次完成中断 → **两个核的服务区间确实重叠**，
本测量方法对服务包络重叠是敏感的。这不支持把 chain 的收益解释成设备重叠，也不直接测量纯计算阶段的重叠。

两个 `ioctl` 调用窗口重叠本身不算硬件重叠（`T_pair` 就是窗口量）。重新从原始 `pair` 时间戳计算，两轮 `P_cross` 各 64 次的服务和均超过共同窗口，差值中位数均为 126436 ns；在两个服务区间均包含于共同窗口的前提下，这是服务区间交集长度的下界。两轮 `P_same` 各 64 次均未出现正差值；这个负结果本身不能证明零重叠，串行判断同时依赖已审计的驱动调度机制。

## 测量方法上的两个硬约束

实现并发组时先遇到两个软件路径上的约束，记录下来：

1. **同进程两个线程、各自 fd 的并发提交会丢写回。** 单线程 preflight 每次都能正确写回；
   改成两线程同时提交后，两边 `hw_elapse_time` 非零、完成位正常，但输出始终全 NaN，
   延时 20 ms 重读仍是 NaN。per-fd IOMMU domain 切换或映射竞争是待验证的根因假说；
   尚无 domain ID、实际页表与切换时序记录可确认设备用了错误页表。**该配置下不能可靠测量同进程双 fd 并发，不推广到共享 fd 的双线程配置。**
2. **`fork` 后的子进程不能复用父进程的 BO 映射。** `rknpu_gem.c:1147` 给 mmap 设了
   `VM_DONTCOPY`，子进程对继承来的 `bo.ptr` 写入直接 SIGSEGV。因此并发进程必须各自
   `rocket_open()` 并各自建立 BO。

最终并发组是**两个进程、各一个 fd、各自算子上下文**，用管道 barrier 同时放行——
这正是此前 [多核调度](MULTICORE-SCHEDULING-PROFILING.md) 的配置。它满足“同时提交、独立上下文、
单核 mask 1/2”的测量要求，但不满足“同一个进程里的两个线程”；本报告不声称线程版可通过。

## 记录与复跑

每个 Submit 记录：`requested_mask`/`actual_mask`、`task_count`、`int_status`、`irq_delta`、
`driver_service_ns`、以及 host 的 `host_begin_ns`/`ioctl_begin_ns`/`ioctl_end_ns`/`host_done_ns`。
每个 arm 另记录 `wall_ns`（提交到输出下载/校验完成，对应上表墙钟列）与 `device_service_sum_ns`（各 Submit 的驱动服务包络之和）。
前者是 Host 端到端量；后者在并发时可重叠累计，不是墙钟，也不是纯硬件计算时间。并发组的 `pair_window` 记录 `T_pair`、服务和、`wall_ns` 与两核中断。

可获得的模块性能计数器仍只有 [同核重叠实验](SAME-CORE-OVERLAP.md) 列出的四类：
驱动服务包络、完成位、每核中断和块位图消融；RK3588 没有可读的模块级 byte/event 计数器。

```bash
# 板端：matmul-lut 回归 + 两轮 gemm-gemv + 位图消融探索
bash research/custom-ops/run-overlap-board.sh

# 离线复核证据（无需设备）
python3 research/custom-ops/overlap_verify.py \
  research/custom-ops/results/2026-10-14/overlap-20261014-155212

# 本机负例（无需设备）
python3 research/custom-ops/overlap_verify_test.py
```

入口：`tools/c/overlap_probe.c`（两个 suite、链式/放大/并发组、host 布局测试）、
`tools/python/overlap_verify.py`（两套 suite 的独立校验与配对统计）、
`tests/python/overlap_verify_test.py`（26 个正/负例）。
板端 `ctest` 与主机全绿；`kernel-after.log` 只有探索臂的三次受控 `job timeout`/`soft reset`，
无 IOMMU fault。范围：Core 0/1、单 task primitive、厂商 blocking Submit；不推广到 `rocket` 主线路、RK3576、
K>256 的 K 分片编排或线程版并发。
