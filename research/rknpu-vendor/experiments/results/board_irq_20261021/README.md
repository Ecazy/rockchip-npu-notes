# 中断状态置位窗口与驱动时间锚点（2026-10-21，板端）

目的：换掉语义无法校验的 `S_STATUS`，改用**驱动自己就在读**的中断状态字，
并补齐"提交入口 / ioctl 返回 / 采样"三者的同一时钟锚点。
**不输出任何 regcmd 位置。**

- 读回：`INTERRUPT_STATUS (0x0028)` + `INTERRUPT_RAW_STATUS (0x002c)`，每个 run 一个快照
- 负载：`min_conv_exp --fp16`（已验证 BIT-EXACT）与 `min_conv_exp --fp16 --iw 32`（同）
- 相位：0–120 µs，步长 4 µs，每相位 6 次；两轮各 186 run
- 配对：ABBA 区组 10 组 × 4 次提交 = 40 次
- 原始数据：`irqA/`、`irqB/`（manifest + runs + out + meta）、`abba.csv`
- 分析产物：`analysis/{report.md,summary.json,bins.csv}`

## 1. 安全性（先看这个）

| 检查 | 结果 |
|---|---|
| 提交次数 | 372（扫描）+ 40（配对）= **412** |
| `RESULT: BIT-EXACT` | **412 / 412** |
| `SUBMIT ret=0` | 412 / 412 |
| dmesg 错误计数（`invalid irq status`/`job timeout`/`failed to wait job`/`soft reset`） | 采集前后**均为 84**（无新增） |

读取 `INTERRUPT_STATUS` **没有**干扰驱动的 IRQ 路径——这是读这个寄存器时最担心的风险。

## 2. 主要发现

### 2.1 置位位是「DPU 对应中断位的置位窗口」，不是块完成脉冲

> 评审修正：不要再叫「组在飞行 / 空闲」。**未置位不等于空闲，置位也尚未证明等于持续计算**；
> 组位与提交奇偶的关联保留，但它不等于已识别当前执行 bank。

`INTERRUPT_STATUS` 只出现过 `0x0100`（DPU_0）或 `0x0200`（DPU_1），**从不同时出现**。
置位从约 11–18 µs 一直持续到作业结束，远超单个块的完成时刻。
因此**不能**把它读成"某块刚完成"。之前的措辞已撤。

### 2.2 组号与提交序号的奇偶严格对应

| 负载 | DPU_0 | DPU_1 |
|---|---|---|
| fp16 | 29 次，**全部偶数提交序号** | 22 次，**全部奇数提交序号** |
| iw32 | 32 次，**全部偶数提交序号** | 22 次，**全部奇数提交序号** |

合并 105 个置位样本，**无一例外**，且跨进程仍然成立（相邻 run 间 13 次 DPU_1→DPU_0、12 次 DPU_0→DPU_1）。
⇒ 乒乓组随**提交次数**翻转，且这个位能可靠标出当前组。

### 2.3 清除沿与驱动报告的 `hw_elapse` 高度相关

> 评审修正：只能表述为「观测到中断状态清除区间；该区间与驱动报告时长高度相关，
> 符合 IRQ 路径清位的解释」。`hw_elapse` 本身含中断与驱动路径，**不是纯硬件作业时长**，
> 因此**不能**升级成「硬件作业结束时间」。本节 +5.0 µs 等数值是用窄区间算的，
> 按读取区间修正后**待复算**（存档未保存 `hw_elapse`）。

用"单一阈值能否分开置位/未置位"做对照（φ ≥ 20 µs 的样本，阈值为样本内拟合）：

| 负载 | 只用 φ | 只用 φ − hw_elapse |
|---|---|---|
| fp16 | 0.727 | **0.992**（阈值 4.1 µs） |
| iw32 | 0.762 | **0.992**（阈值 7.0 µs） |

⇒ 清除发生在**作业结束**，而不是某个固定的提交后时刻。这是"IRQ 路径在作业结束时清位"的间接证据。
`ioctl 返回后置位比例 = 0`（两负载共 43 个返回后样本），与之一致。

### 2.4 上升沿的机理**未解释**

p(置位) 在 fp16 于 ~14 µs、iw32 于 ~18 µs 首次超过 0.5。这个时刻**不能**当作"启动"或"完成"，
它可能来自驱动写 `OPERATION_ENABLE`、组切换、采样延迟或它们的组合。未做定标。

### 2.5 配对扰动：**未检出**（初版结论已撤回）

ABBA 区组（每组 4 次提交，两臂各占一个偶数和一个奇数序号，使乒乓组奇偶抵消）：

> 区组数 10；区组内均值差中位数 **−0.9 µs**，95% 区间 **[−13.4, +12.0] µs**；均值 +0.3 µs。

区间跨 0 ⇒在本样本量下**测不到**采样带来的时长扰动。
初版两两配对给出的"采样臂快 10.8 µs"是**奇偶混杂**造成的伪信号（irqB 中偶数提交序号
`hw_elapse` 中位数 60.4 µs vs 奇数 28.0 µs），已撤回。

### 2.6 采样生命周期与返回锚点一致

372 个扫描 run 中有 86 个"无样本"，**全部**满足"请求相位晚于 ioctl 返回"
（中位请求 94.0 µs vs 中位返回 48.6 µs）。这符合设计：超出作业的相位不应产生样本。

## 3. 没有证明的（与 2.x 同等重要）

- 不给出任何 regcmd 位置、task 内时刻或 per-regcmd 时长；
- 上升沿语义未知；`STATUS_0/STATUS_1`（`S_STATUS`）仍然没有可用判据；
- `submit → kick` 偏移未标定；由下降沿反推只能给出**估计**，且阈值是样本内拟合；
- 下降沿对齐是"IRQ 清除"的**间接**证据，IRQ 时刻本身未被直接观测；
- 未验证 `0x0028`/`0x002c` 的读是否对**其它**负载/多 task 链同样无副作用（本轮到单 task）；
- 结论仅适用于本板、本驱动版本（0.9.8 / 6.1.43）与这两个负载。

## 4. 与既有结论的关系

- `S_STATUS` 路线停在"字可读、语义不可校验"，本轮**没有**再依赖它；
- 驱动侧现在有一个**可用的同钟时间锚点**（ioctl 返回）可用于后续任何时间测量；
- P0/P1/P2 的验收状态不变：**per-regcmd timing 仍未建立**，本轮只交付"模块/组级窗口 + 时间锚点"的板端证据。
