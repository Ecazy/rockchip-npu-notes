# S_STATUS 模块活动采样：首轮（2026-10-21，板端）

目的：在**通过自身数值校验**的负载上，先回答"四个模块的 `S_STATUS` 能不能稳定区分
idle / busy 和不同负载阶段"，**不涉及**任何 regcmd 位置结论。

- 负载 A：`min_conv_exp --pattern --fp16`（连续 5 次 `BIT-EXACT (fp16)`，`hw_elapse` 62–113 µs）
- 负载 B：`min_conv_exp --pattern --fp16 --iw 16`（同样 `BIT-EXACT (fp16)`，77 µs）
- 采样：`CAP=1`、`SELECT=5`（一次读 4 个模块状态）、`MIN_EFF=1`、`OP_IDX=-1`、
  `PREOPEN_POWER=1`；相位随机化，每相位 8 次；A 组 120 run / 114 样本，B 组 64 样本。
- 原始数据：`statusA/`、`statusB/`（manifest + runs + 分析报告）。

## 1. 读回值的集合（这是本轮唯一稳的东西）

| 模块 | 负载 A（114 样本） | 负载 B（64 样本） |
|---|---|---|
| CNA `0x1000` | `0x0`×60、`0xc`×51、`0x5`×2、`0x00010008`×1 | `0x0`×34、`0xc`×28、`0x5`×1、`0x00010008`×1 |
| CORE `0x3000` | `0x0`×58、`0xc`×51、`0x5`×4、`0x00010008`×1 | `0x0`×34、`0xc`×28、`0x5`×1、`0x00010008`×1 |
| DPU `0x4000` | `0x0`×59、`0xc`×50、`0x5`×4、`0x00010008`×1 | `0x0`×34、`0xc`×27、`0x5`×2、`0x00010008`×1 |
| DPU_RDMA `0x5000` | **`0x0001000a`×114（恒定）** | `0x0001000a`×63、`0x0`×1 |

**结论 1（正面）**：状态字可读、取值稳定、跨 run 重复性好（177+ 样本只出现 4 种取值）。

**结论 2（负面）**：两个计算量相差明显的已验证负载，**取值分布几乎一样**。
因此**目前没有证据**表明 `S_STATUS` 能区分负载阶段——至少在被采到的相位上不能。

**结论 3**：`DPU_RDMA` 在 177/178 个样本里恒为 `0x0001000a`。

## 2. 解码本身还没被验证

按 `ppu-rknn-capture/registers.xml`，四个 `S_STATUS` 的位域是：

```
STATUS_0 = bits[1:0]      STATUS_1 = bits[17:16]
bits[15:2]、[31:18] = RESERVED
```

而实际在变化的是 **bit 2 / bit 3（属于 RESERVED 区）**：

| 观测值 | STATUS_0 | STATUS_1 | 备注 |
|---|---|---|---|
| `0x0000000c` | 0 | 0 | 变化的是 reserved 位 2/3 |
| `0x00000005` | 1 | 0 | 同上 |
| `0x00010008` | 0 | 1 | 同上 |
| `0x0001000a` | 2 | 1 | RDMA 恒定值 |

仓库里的 `status_busy()`（`status0 ∈ {1,2}` 或 `status1 ∈ {1,2}`）是**从 SDPA 实验沿用的启发式**，
不是厂商文档语义。按它解码，RDMA 会**永远**被判 busy。

所以"idle/busy 可区分"这一条**尚未成立**：我们只证明了字可读且稳定，
没有证明这些位对应"模块正在执行"。

## 3. 采样窗口问题（复述，未解决）

所有样本的实际相位都 ≥ 17.2 µs（请求 φ=0/4/8 µs 的也都落在 ~17 µs），
说明在这两个负载上采样延迟底仍是 ~17 µs；而模块大概率只在开头忙，
这段窗口目前**采不到**。

## 3b. 离线查证：没有任何可及的实现解码 `S_STATUS`（2026-10-21）

查了三处：

| 来源 | 是否解码 S_STATUS |
|---|---|
| 内核驱动 `rknpu098/drivers/rknpu/`（`rknpu_job.c`/`rknpu_drv.c`/头文件） | **否**：全文没有 `S_STATUS` 引用 |
| mesa rocket 驱动（`refs/mesa/.../rocket/`） | **否**：只有命令构造（`rkt_regcmd.c`），无执行/等待代码 |
| vendor `librocketnpu`（`refs/orangepi5plus-npu`） | **否**：只有寄存器名定义（`rnpu_registers.h`） |

驱动实际用的是另外两样东西：

- **每块完成中断**：IRQ 路径读 `RKNPU_OFFSET_INT_STATUS` 与 `job->int_mask` 比对
  （本负载 `int_mask = 0x300`，dmesg 里 "require mask: 0x300" 即此）；
- **`PC_TASK_STATUS (0x003c)`**：只在**超时错误路径**上读，用于报告 `task_counter`。

也就是说：`STATUS_0`/`STATUS_1` 两个 2-bit 字段的取值含义（1 是什么、2 是什么）
**在任何可及源码里都没有定义**；我们观察到的变化发生在 `registers.xml` 标为
RESERVED 的 bit2/bit3 上。因此 `status_busy()` 这个启发式**无法离线校验**，
继续用它得出"模块忙闲"结论就是猜测。

## 4. 下一步（按可行性排序）

0. **优先换读回量**：`INTERRUPT_STATUS (0x0028)` / `INTERRUPT_RAW_STATUS (0x002c)`
   的**每块完成位有驱动级证据**（`job->int_mask` 比对），比 `S_STATUS` 语义清楚得多。
   在任务执行中采样它，得到的是"哪个块已经完成"的**完成事件**，而不是含义不明的 busy 标志。
   代价：它位于 PC 页（0x0xxx），当前 `RAW_OFF` 白名单禁止，需要单独开一个**只读**白名单项。


1. **离线定标解码**：在厂商驱动/参考实现里找 `S_STATUS` 的读取与判据（不是猜），
   用"同一负载、同一相位"的变化去对照位域；否则 RDMA 恒 busy 这类现象无法解释。
2. **受控激励**：用只压一个模块的负载（例如纯 DMA / 纯 DPU）对比同一相位的状态字分布，
   看是否出现只在对应模块上不同的位型。
3. **把窗口推进到任务开头**：当前 ~17 µs 的延迟底决定了 20 µs 以内的阶段不可观测。
4. 这些都通过后，才谈 `P(module busy | φ)` 曲线；**仍不输出 regcmd 位置**。
