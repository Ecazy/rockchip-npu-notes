# 单 task 内多快照可行性（2026-10-21，板端）

> **评审修正（2026-10-21）**：本文早期的边沿区间只用相邻样本的 `t_ns` 夹逼，**报得偏窄**；
> 现已改为按每次快照自己的读取区间 `[gb, ge]` 保守包围
> （`clear→set` 的转变 `T` 满足 `gb(clear) < T <= ge(set)`）。
> 例：`wide/w01` 下降沿 旧 `(81.958, 84.583]` → 新 `[82.541, 86.041]` µs。
> 另外：**2.625 µs 是相邻间隔中位数，不是精度保证，也不是 ±2.6 µs 误差界。**
> 文中凡涉及 `fall − hw` 与"窗口宽度 ≈ hw − 常数"的具体数值，仍是窄区间的结果，
> 按读取区间修正后**待复算**（存档未保存 `hw_elapse`）。

问题：一次提交里能不能取多个快照，从而**在同一个 task 内**解析出状态变化？
前面的相位扫描每个 run 只有一个样本，所有结论都依赖"逐次运行平稳"这个假设。

- 负载：`min_conv_exp --fp16`（已验证 BIT-EXACT）
- 配置：`CAP=8`、`PHASE_NS=0`、`SPIN_NS=1000`（请求 1 µs 周期）、`PREOPEN_POWER=1`、
  `RAW_OFF=0x0028`（`INTERRUPT_STATUS`）
- 20 次运行；数据 `intra/`，分析 `analysis/{report.md,summary.json,edges.csv}`

## 结果

| 指标 | p10 | p50 | p90 |
|---|---|---|---|
| 每次运行的快照数（中位数） | — | **8**（打满 cap） | — |
| 相邻快照间隔 | 2.92 µs | **3.21 µs** | 8.75 µs |
| 单次读取区间 | 0.88 µs | **1.17 µs** | 2.04 µs |
| 覆盖跨度 | 23.92 µs | 34.71 µs | 42.00 µs |
| 首个快照相位 | 9.04 µs | 11.67 µs | 30.04 µs |

- 请求 1 µs 周期，实际 **3.2 µs**（约 3 倍）；这是**间隔**，不是精度保证；
- **上升沿被同一次运行夹住：4/20；下降沿：5/20；两边沿都夹住：3/20**
  （其余运行整段都 set 或整段都 clear，无法夹逼，未作猜测）。

### 单次运行里完整解析的实例

```
i15:  clear(8.8) → SET(13.7, 16.9, 20.1, 23.3) → clear(26.5, 29.5, 32.7)
i17:  clear(13.4) → SET(19.0 … 36.5)
i02:  SET(19.2) → clear(28.3 … 50.2)
i01:  SET(19.5 … 72.3)（窗口比采样跨度更长）
```

`i15` 同时夹住了两个边沿：上升 ∈ (8.8, 13.7] µs，下降 ∈ (23.3, 26.5] µs，
位窗口宽度下界中位数 **9.6 µs**。

## 结论

- **可以在单 task 内取到 8 个快照**，时间分辨率约 **3 µs**，读取不确定度约 **1.2 µs**；
- 因此"窗口"这类 state 变化**可以在一次运行内被夹住**，不必依赖跨运行平稳性——
  这比单快照相位扫描强一个层次；
- 首发快照仍有约 **9 µs** 的下限，任务最开头仍不可观测；
- 只有约 1/4–1/2 的运行能夹住某个边沿，要提高命中率应缩小间隔或延长负载。

## 补充实验：间隔上限、绑核、CAP 与整窗解析（2026-10-21）

负载换成更长的已验证配置 `min_conv_exp --fp16 --iw 32 --ih 32`（中位 74 µs，6/6 BIT-EXACT）。

### 间隔能压到多少（各 12 run，`CAP=8`）

| 配置 | 间隔 p50 / p90 (µs) | 首个快照 (µs) | ≥3 段的运行 |
|---|---|---|---|
| `SPIN_NS=1000`（基线） | 3.21 / 5.83 | 7.88 | 4/12 |
| `SPIN_NS=500` | 3.50 / 7.88 | 8.90 | 5/12 |
| `SPIN_NS=200` | 3.21 / 8.17 | 8.17 | 1/12 |
| **`SPIN_NS=0`（背靠背）** | **2.62 / 6.12** | **5.98** | 0/12 |
| `SPIN_NS=1000` + 绑 CPU7 | 7.29 / 8.75 | 9.04 | 3/12 |
| `SPIN_NS=0` + 绑 CPU7 | 6.12 / 6.42 | 7.29 | 2/12 |

- **地板是 2.62 µs**（背靠背），由"每样本 3 次 MMIO 读 + 循环开销"决定，不是 pacing；
- **绑核反而更差**（3.21→7.29、2.62→6.12）——与之前延迟拆解里"单独绑核无收益"一致，
  该优化项据此**关闭**；
- `SPIN_NS` 从 1000 降到 200/500 无单调改善（噪声主导）。

### 加大 CAP 才能把整个窗口装进一次运行（`CAP=32`、`SPIN_NS=0`、12 run）

| 指标 | 值 |
|---|---|
| 每次运行快照数 | 中位 **23**（打满 32 的 4 次） |
| 相邻间隔 | p50 **2.62 µs** |
| 覆盖跨度 | p50 **84.6 µs** |
| 上升沿被夹住 | **9/12** |
| 下降沿被夹住 | **8/12** |
| **完整 `clear→set→clear`（≥3 段）** | **8/12** |
| 同一次运行内测得的窗口宽度下界 | min 0.0 / p50 **7.9** / max 56.0 µs |

实例（`wide/w01.csv`，hw=77.9 µs）：

```
ccccSSSSSSSSSSSSSSSSSSSSSSSSSccccc     32 个快照，跨度 84.6 µs，三段齐全
```

对照 `CAP=8` 时下降沿只有 16/72——**限制因素是覆盖跨度，不是间隔**。要提高整窗命中率应加大 `CAP`。

## 补充：上升沿 vs 下降沿在**同一次运行内**的关系（2026-10-21）

`CAP=32`、`SPIN_NS=0`，各配置 6 次（仅取 **6/6 BIT-EXACT** 的配置）：

| 配置 | hw p50 | **上升沿 p50（范围）** | 下降沿 − hw p50 | 窗口宽度 p50 |
|---|---|---|---|---|
| `--fp16`（8×8 k3） | 20.7 µs | **12.0**（11.7–12.8） | 4.4 µs | 13.1 µs |
| `--fp16 --iw 16 --ih 16` | 59.2 µs | **14.5**（12.8–16.5） | 4.2 µs | 46.7 µs |
| `--fp16 --iw 32 --ih 32` | 30.2 µs | **24.2**（21.0–27.6） | 2.6 µs | 8.0 µs |
| ~~`--kw 1` 两个变体~~ | — | — | — | **0/6 BIT-EXACT，作废** |

单次运行内的定量结论（hw 跨 27–86 µs，13 个完整窗口）：

- **下降沿 − `hw_elapse` = +5.0 µs**（p50，范围 2.9–6.1，**窄区间算法**）⇒ 清除点与驱动报告时长高度相关；按读取区间修正后**待复算**，且 `hw_elapse` 不是纯硬件时长；
- **窗口宽度与 `hw_elapse` 的相关系数 0.997**（窄区间算法，待复算）；
- **上升沿 12.0 / 14.5 / 24.2 µs 随负载变化**，不是固定常数。

### 一个被推翻的假设

"窗口起点 = 硬件 kick"**不成立**：由 `job_end = kick + hw` 与 `fall − hw ≈ +5 µs` 可得
kick ≈ 提交入口附近（≤5 µs），而上升沿要到 12–24 µs 才发生。
⇒ **上升沿标记的是作业内部相位，不是作业开始**；这正是它可能成为相位信号的原因，
但它与"作业时长""输入尺寸""首个中断"等解释尚未分离。

## 补充：上升沿跟哪一侧的工作量走（2026-10-21）

4 个**均 6/6 BIT-EXACT** 的配置（`CAP=32`、`SPIN_NS=0`）：

| 配置 | hw 中位 | **rise 中位（范围）** | CNA 工作量 `icr·kw·kh·oh·ow` | DPU 工作量 `ocr·oh·ow` |
|---|---|---|---|---|
| 8×8 ic16 oc16 | 37.9 µs | **11.7**（11.2–12.0） | 1728 | 1024 |
| 8×8 ic16 **oc32** | 17.2 µs | **12.0**（10.9–13.6） | 1728 | 2048 |
| 16×16 ic16 oc16 | 51.8 µs | **14.8**（12.4–16.3） | 6912 | 4096 |
| 16×16 ic16 **oc8** | 21.6 µs | **16.0**（13.0–16.8） | 6912 | 2048 |

| 相关 | 系数 |
|---|---|
| rise vs `hw_elapse` | **0.109** |
| rise vs CNA 工作量 | **0.970** |
| rise vs DPU 工作量 | 0.533 |

**支持的部分**：两组"只改 `oc`"的对照（8×8 的 oc16→oc32、16×16 的 oc16→oc8）里，
**rise 都没有变化**（11.7→12.0、14.8→16.0，区间重叠），而 `hw` 变化很大
（37.9→17.2、51.8→21.6）⇒ **rise 既不跟作业时长走，也不跟输出通道数走**。

**不支持过强结论的部分**：
- 想单独隔离 CNA 的 `--ic 32` 两个配置 **0/6 BIT-EXACT**，无法使用，所以"CNA 工作量"和
  "空间尺寸 `ow·oh`"在本轮**没有被分开**；
- 只有 4 个点，且 rise 的总变幅只有 11.7–16.0 µs（4 倍工作量换来 4.3 µs）。

**当前最保守的表述（已被下一节推翻）**：上升沿与**输入/空间一侧**的量有关，
与输出通道数和总时长无关。

## 补充：补齐 `ic` 轴后，上一节的结论被推翻（2026-10-21）

`--ic` 轴需要第二档判据（fp16 累加顺序导致非逐位一致，见 `workload_verdict.py`）：

| 配置 | 档位 | hw 中位 | **rise 中位（范围）** | CNA 工作量 |
|---|---|---|---|---|
| 8×8 ic16(real3) | bit-exact | 59.4 µs | **12.1**（10.6–15.0） | 1728 |
| 8×8 ic32 | ulp-bounded | 23.5 µs | **12.5**（11.2–13.7） | 18432 |
| 8×8 ic48 | ulp-bounded | 62.0 µs | **16.0**（13.3–16.9） | 27648 |
| 8×8 ic64 | ulp-bounded | 43.6 µs | **14.9**（13.0–16.5） | 36864 |
| 8×8 oc32 | bit-exact | 20.6 µs | **13.1**（11.8–16.0） | 1728 |
| 16×16 ic16 | bit-exact | 60.1 µs | **16.3**（13.0–17.8） | 6912 |
| ~~8×8 ic16~~ | **rejected**（45/1024, max ulp **140**） | — | — | — |

| 相关（n=6） | 系数 |
|---|---|
| rise vs `hw_elapse` | 0.551 |
| rise vs CNA 工作量 | **0.441**（上一节曾为 0.970） |
| rise vs DPU 工作量 | 0.485 |

**结论**：跨越 **21× CNA 工作量**、2× DPU 工作量、20–62 µs 时长，rise 只在
**12.1–16.3 µs** 之间变化，且没有任何工作量代理量能解释它（相关 0.44–0.55，n=6）。
上一节"与 CNA 工作量强相关"（0.970）**已撤回**——那是 4 个点里空间尺寸与 CNA 共同变化造成的假象。

⇒ 上升沿更像**与配置无关的固定相位延迟**，而不是"CNA→DPU 相位边界"。
这对它是**负面**结论：它作为相位信号的价值下降。

## 补充：NPU 频率是不是那个"固定延迟"的时钟？（2026-10-21，受控变量）

`devfreq` 有 `userspace` governor，频率 300 MHz–1 GHz。只改 governor/频率，**不写任何 NPU 寄存器**；
测完已恢复原 governor `rknpu_ondemand`、`cur_freq` 回到 1000 MHz。

| 目标频率 | 实测 cur | hw 中位 | **rise 中位（范围）** | rise×freq |
|---|---|---|---|---|
| 300 MHz | 300 | 20.1 µs | **15.75**（12.8–19.1） | 4.7 千周期 |
| 500 MHz | 500 | 60.1 µs | **13.71**（12.4–13.9） | 6.9 千周期 |
| 700 MHz | 700 | — | **未夹住边沿（5 run 全缺）** | — |
| 1000 MHz | 1000 | 14.6 µs | **13.20**（11.7–14.7） | 13.2 千周期 |

（每档 5 run，**全部 5/5 BIT-EXACT**；700 MHz 那档只是没夹住边沿，按缺失记录，不当作一致。）

**结论**：
- rise 在**墙钟**上近乎恒定（13.2–15.8 µs，300 MHz 时略大 2.5 µs）；
- `rise × freq` 约 **4.7 千 → 13.2 千周期**（**2.8×**）⇒ **不随 NPU 周期数成比例**；
- 但这**不足以**断言"由 NPU 时钟之外的路径决定"：只有 3 个频率点、5 run/档，
  "固定开销 + 可变硬件阶段"这类混合机制同样能解释。

可以确定的是：它**不适合当作相位信号**；它的语义**未识别**。

## 没有证明的

- 边沿是**区间**不是点值；精度直接受 3.2 µs 间隔限制；
- 窗口宽度是**下界**：两个边沿各自只是一个区间，真实窗口宽度介于该下界与"再加两个间隔"之间；
- 仍不涉及任何 regcmd 位置或 per-regcmd 时长；
- `SPIN_NS` 只是"周期下限"，实际间隔由调度决定，p90 达 8.75 µs；
- 仅适用于本板、本驱动版本与该负载；多 task 场景未测试（见 `board_multitask_20261021`，
  那条线因链不稳定已停）。
