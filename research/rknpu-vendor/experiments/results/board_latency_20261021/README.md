# 采样时序拆解（2026-10-21，板端）

目标不是"让样本发生在 φ"，而是回答**一次相位采样能不能落进任务窗口**，并把延迟归因到阶段，
再逐个验证优化项。负载：`min_conv --dup-config --iw 32`（单 task，实测 `hw_elapse`
约 70–100 µs 的长任务，先做校准）。每组 5 次运行、每次 1 个样本。

原始数据：`lat/`（每次运行一份 blockwatch CSV + META 日志 + 程序输出）。
分析产物：`analysis/{latency.json,report.md}`（由 `analyze_sampler_latency.py` 生成）。

## 1. 结果

| 变体 | 窗口覆盖率 | 迟到 p50 | 迟到 p90 | 读取区间 p50 |
|---|---|---|---|---|
| `base`（现状） | 50% | 32.1 µs | 50.3 µs | 1.17 µs |
| `prefault`（预触页 + 预热 MMIO 映射） | 0% | 46.2 µs | 55.3 µs | 1.75 µs |
| `preopen_power`（运行前打开电源 debugfs fd） | **80%** | **8.6 µs** | 33.7 µs | 1.46 µs |
| `pin_cpu`（采样线程绑 CPU7） | 20% | 41.6 µs | 48.6 µs | 1.75 µs |
| `all`（三者同时） | **80%** | 11.8 µs | 14.8 µs | 1.46 µs |

阶段耗时（p50，来自 META 的 `lat_*_ns`）：

| 变体 | arm→相位结束 | **电源检查** | 电源后→首读 |
|---|---|---|---|
| `base` | 1.5 µs | **27.9 µs** | 2.6 µs |
| `preopen_power` | 1.2 µs | **4.7 µs** | 1.5 µs |
| `all` | 1.0 µs | 1.0–7.6 µs | 1.7 µs |

## 2. 结论

1. **主延迟项是电源检查本身**，不是线程调度、也不是缺页：`base` 里 `lat_power_begin →
   lat_power_end` 占 21–43 µs，主要来自运行中**首次** `open()` + `pread()`
   debugfs 电源文件。把它移到 arm 之前（`PREOPEN_POWER=1`）后降到约 5 µs，
   迟到从 32.1 µs 降到 8.6 µs，覆盖率从 50% 升到 80%。
2. **预触页无效**（46.2 µs，比 base 还差，n=5 属噪声）⇒ 缺页不是瓶颈，
   这条优化不必再花力气。
3. **单独绑核无效**（41.6 µs）。`all` 相对 `preopen` 没有可辨收益（11.8 vs 8.6 µs，n=5），
   所以绑核暂时不作为默认项；若要再试，应配 `SCHED_FIFO` 并确认不挤占提交线程/中断。
4. 没有任何变体削弱电源保障：`all` 与 `preopen` 里**首读前仍然必查一次**电源，
   剩余约 5 µs 就是这次 `pread` 的成本。
5. 迟到 p90 仍偏大（`preopen` 33.7 µs），说明尾部还受调度影响；样本量只有 5，需要更多轮次才能定论。

## 3. 对路线 A 的意义

- 对 70–100 µs 的长 task：`preopen` 后 80% 样本落在窗口内，**相位扫描已经可用**。
- 对约 7 µs 的 SDPA task：剩余 8.6 µs 的中位迟到仍然意味着**大多数样本会落在任务之后**。
  要支撑短 task，还需要把"首读前的那次 `pread`"移出关键路径——这需要驱动侧提供更廉价的
  电源保证，或允许在已确认持电源的窗口内跳过重复检查（属驱动改动，未做）。
- 本轮的 50–80 µs 只在 `--iw 32` 这一种负载上测过；**不能**据此推断长链里后续短 task 永不可采。
