# 测量模型与能力边界（RK3588 / RKNPU 0.9.8，2026-10-21 汇总）

> ## 阶段结论（收口口径）
>
> **在本板现有内核、可用追踪点和已验证访问方式下，用户态 MMIO ＋ ftrace
> 尚不能可靠恢复 `PC_OP_EN` 写入时刻、块级完成、执行 bank 或 regcmd 位置；
> 继续探索的预期收益不足，停止新增板端探测。**
>
> 这些量也**不**只是"差一个不可内联观测点"：改驱动或 kprobe 能补软件事件，
> 但 **bank、块级完成与 regcmd 进度仍需要可解释的硬件信号**，
> 不能承诺换内核就能全部获得。
>
> 本阶段可交付：采样与追踪工具、原始数据、回归测试；限定负载下的中断状态窗口、
> 驱动函数入口与 PM 调用序列；已撤回假设、失败模式与停用配置。
>
> **per-regcmd timing 未建立，P0/P1 未通过。**
> 本轮可验收为**一轮完成归档的可观测性探索**，
> **不可验收为目标能力已实现**。
>
> **重开条件**（只在观测条件改变时）：可修改的内核、可用的指令级探针、
> 或经过确认的硬件 trace／厂商接口。**不稳定多 task 链继续停用。**

这份文档把目前为止**已经站得住的东西**和**只是模型/推测的东西**分开列清，
每条给证据等级：

| 等级 | 含义 |
|---|---|
| **实测** | 板端采集到的数据直接支持，且给出了样本量与区间 |
| **间接** | 由已实测的量推出，依赖明确列出的前提 |
| **模型** | 能解释现有全部观测，但**未被判别实验证实** |
| **已撤回** | 曾经写过、后被数据推翻，保留以示边界 |
| **未建立** | 尝试过或评估过，但没有取得可用结论 |

适用范围：本板、驱动 `rknpu 0.9.8.1` / 内核 `6.1.43-rockchip-rk3588-rknpu098`、
单 core、本文列出的那些负载。**per-regcmd timing 仍未建立**。

## 1. 仪器：一次采样到底测了什么

### 1.1 采样通路

采样线程在提交 ioctl 内部启动，读 `/dev/mem` 映射的 `0xfdab0000` 窗口（3 个 core，步长 `0x10000`）。
每个样本至少包含 **3 次 MMIO 读**（时间戳 + 目标寄存器 + 时间戳），因此样本本身带一个
**读取区间**。

| 量 | 值（p50） | 等级 |
|---|---|---|
| 单次读取区间（3 读） | **1.17 µs**（p10 0.88 / p90 2.04） | 实测 |
| 相邻快照间隔（`SPIN_NS=0` 背靠背） | **2.62 µs**（p90 6.12） | 实测 |
| 相邻快照间隔（`SPIN_NS=1000`） | 3.21 µs（p90 5.83） | 实测 |
| 首个快照相位 | **9.33 µs**（p10 8.75） | 实测 |

### 1.2 相位滞后的来源（已归因，不再是黑箱）

请求相位与实际相位之间 ~9–17 µs 的差，拆开是：

| 分量 | 量级 | 等级 |
|---|---|---|
| 首读前的电源 debugfs `open+pread` | 21–43 µs →预开后 **~5 µs** | 实测（变量对照） |
| ~~submit → 硬件 kick 的真实偏移 ≤ 5.5 µs~~ | **已撤回**：条件估计的前提（kick 在提交入口附近）不成立；实测见下一行 | 已撤回 |
| **调度路径入口（ftrace 实测）** | hook 入口后 **p50 15.9 µs**（13.2–33.0，n=6），其中 **6.2–14.0 µs 是我们自己的 LD_PRELOAD wrapper 开销**。这是 **kick 的下界**，不是 kick | **实测**（[board_ftrace](../rknpu-vendor/experiments/results/board_ftrace_20261021/README.md)） |
| 线程唤醒 + 相位等待误差 | ~1.2 µs | 实测 |
| 预触页、绑核 | **无收益**（绑核反而更差） | 实测（负结果） |

⇒ 早期把全部延迟算在"电源检查"上的说法**不成立**；其中约 5 µs 是真实的硬件提交偏移。

### 1.2b 上升沿：可用证据只到"与调度路径入口的区间关系"

这里先后写过两次错误结论：先是"窗口起点 = kick 是错的"，后是"上升沿 = kick"。
两次都超出了数据能支持的范围。按源码核对后的准确口径：

**源码事实**（`rknpu098/rknpu_job.c`）：`rknpu_job_next()` 有两条早退（`soft_reseting`、
`subcore_data->job` 忙或 todo_list 空），**都不设** `hw_commit_time`、**都不写** `PC_OP_EN`。
真正的提交在 `rknpu_job_commit → rknpu_job_subcore_commit → ..._commit_pc`，
全是 `static`/`static inline`，**不在 `available_filter_functions`** ⇒ ftrace 拿不到该时刻。

**能测到的**（ftrace，`mono_raw`，原点 = 采样器 `submit_enter`，n=6）：

| 量 | 值 |
|---|---|
| hook 入口 → 真实 ioctl 入口 | 6.2–14.0 µs |
| **调度路径入口**（`job_next` ← `job_schedule`） | **13.2–33.0 µs（p50 15.9）**，是 `kick_rel` 的**下界** |
| IRQ handler 入口 | 65.0–151.3 µs（p50 124.1） |
| `hw_elapse − (IRQ 入口 − 调度入口)` | **1.7–8.5 µs**（与"在 `job_done` 内稍后取时"一致） |
| 上升沿 − 调度路径入口 | **2.8 ~ 15.2 µs（区间）** |
| 下降沿 − IRQ handler 入口 | **−1.5 ~ +7.1 µs（区间）** |
| `job_next` 调用数 / `job_schedule` 调用数 | **2 / 1** |

**可以说的**：中断位的置位与清除**都落在调度入口/IRQ 入口之后的区间内**，
与本批单 job 的提交/完成顺序不矛盾。

**不可以说的**：上升沿"就是" kick（kick 本身仍未测量）；位等于"作业在飞行"；
下降沿等于"硬件作业结束"。这些事件的**硬件语义仍标为未识别**。

### 1.3 分辨率

| 维度 | 能力 | 等级 |
|---|---|---|
| 单次运行内的相邻快照间隔 | p50 **2.625 µs**、p90 6.416 µs（`CAP=32`、背靠背）——这是**间隔**，**不是精度保证，也不是 ±2.6 µs 误差界** | 实测 |
| 单次读取区间 | p50 1.17 µs（p10 0.88 / p90 2.04）——边沿包围必须用它，不能用 `t_ns` 单点 | 实测 |
| 单次运行内的覆盖跨度 | `CAP=32` 时 p50 **84.58 µs**（23 个快照/次） | 实测 |
| 首个快照相位 | **随配置变化**：p50 5.98（`SPIN_NS=0`）～11.67 µs；**不是**硬性的"<9 µs 不可观测"边界 | 实测 |
| 跨运行相位扫描 | 每 run 一个点，依赖"逐次运行平稳" | 实测（并已用 §1.3 的单次内方法取代） |

## 2. 时间基准链

### 2.1 三个锚点，同一时钟

全部来自 `CLOCK_MONOTONIC_RAW`，因此可以直接相减：

| 锚点 | 含义 | 等级 |
|---|---|---|
| `submit_enter_ns` | 用户态进入 submit 路径 | 实测 |
| `lat_ioctl_start_ns` / `lat_ioctl_return_ns` | 真实 ioctl 的进入与返回（用户可见完成） | 实测 |
| `hw_elapse_time` | 驱动报告：`ktime_get()` at `rknpu_job_done()` 减 `hw_commit_time` | 源码（`rknpu_job.c:452` 设 commit、`:481` 算差值） |

### 2.2 驱动侧事实（源码级，版本 `rknpu 0.9.8.1`）

**计时源不同源，必须先说清**：驱动用 `ktime_get()`（**CLOCK_MONOTONIC**），
采样器用 `CLOCK_MONOTONIC_RAW`。两者在短区间内通常只差 NTP/PLL 调频的微小量，
但**没有证据**证明它们同源，因此跨这两套时钟的比较只能当作近似。

**`hw_elapse_time` 的实际跨度**（`rknpu_job.c`）：

| 位置 | 代码 |
|---|---|
| `rknpu_job_next()` | `job->hw_commit_time = ktime_get();`（**在** 调 `rknpu_job_subcore_commit()` 写 `PC_OP_EN` **之前**） |
| `rknpu_job_done()`（IRQ/done 路径） | `now = ktime_get(); job->hw_elapse_time = ktime_sub(now, job->hw_commit_time);` |

⇒ 它包含：写 `OP_EN` 的路径 + 硬件执行 + 中断延迟 + 驱动进入 `job_done` 的延迟。
**它不是纯硬件作业时长**，因此下文不能既把它当硬件结束时间、又另外加一个 `irq_latency`。

**PM / 生命周期（ftrace 实测，3 次运行）**：

| 事实 | 证据 |
|---|---|
| 域由**负载自己的 GEM 引用**打开 | 首个 `rknpu_power_get`(GEM create) → `rknpu_power_on` 相隔 4 µs，比 commit 早数毫秒 |
| **`rknpu_power_off` 全程未出现**，后续运行也无 `power_on` | 3/3 次运行；域**跨运行保持开启**（延迟断电超出观测窗口） |
| **`rknpu_job_next.part.0` 每 job 被调用两次** | 第一次 `<- rknpu_job_schedule`（commit），第二次 `<- rknpu_irq_handler`（派发下一个 job），间隔中位 177 µs |

⇒ 采样器的电源复查之所以能通过，靠的是**负载的 GEM 引用**，不是采样器自身；
分析器只把**第一次** `job_next` 当作 kick。

其余事实：

- `rknpu_job_commit()` 里写 `PC_OP_EN`；
- IRQ 到达时算 `hw_elapse_time = now − hw_commit_time`；
- 完成后 IRQ 路径 `REG_WRITE(0x1ffff, INT_CLEAR)` 清中断状态；
- `task_pp_en = (flags & RKNPU_JOB_PINGPONG)`，整个 job **只写一次**
  `PC_TASK_CONTROL = ((0x6|task_pp_en) << 12) | task_number`；
  驱动**不按 task 写 `S_POINTER`**，task 列表由硬件自己走。

### 2.3 submit → kick：**已由 ftrace 实测**（旧的估计模型作废）

由 `job_end − kick = hw_elapse` 与"IRQ 在作业结束时清位"推得：
置位条件 `φ < kick_rel + hw + irq_latency`；令 `x = φ − hw`，过渡点
`x* = kick_rel + irq_latency` ⇒ **`submit→kick ≤ x*`**。

| 负载 | x* 估计（作废） | 95% 区间 | 等级 |
|---|---|---|---|
| `--fp16` | 5.54 µs | 4.08–6.42 | 作废（模型前提不成立） |
| `--fp16 --iw 32` | 5.10 µs | 4.81–6.42 | 同上 |

**这个估计模型作废**：它假设 kick 在提交入口附近。ftrace 直接测到 commit 在
hook 入口后 13.2–33.0 µs（p50 15.9），其中 6.2–14.0 µs 是 wrapper 自身开销。
`calibrate_kick_offset.py` 保留，但结论只作历史记录，不再引用。

## 3. 可读量各自的意义

### 3.1 `INTERRUPT_STATUS (0x0028)` / `RAW_STATUS (0x002c)` —— 唯一可用的状态量

| 命题 | 证据 | 等级 |
|---|---|---|
| 位域按块分组：每块一对 `_0/_1`（bit0–13） | `registers.xml` + 驱动 `rknpu_fuzz_status` 按对判断 | 实测/源码 |
| 读取**不干扰** IRQ 路径 | 412 次提交全 BIT-EXACT，dmesg 错误计数不变 | 实测 |
| 位的置位/清除都落在调度入口/IRQ 入口之后的区间内 | 上升沿 − 调度入口 = **2.8~15.2 µs**（区间）；下降沿 − IRQ 入口 = **−1.5~+7.1 µs**（区间）；n=6/2 | 实测（关系）/ **语义未识别** |
| 清除区间与驱动报告时长高度相关 | 单一阈值可分性 0.992（φ−hw）vs 0.727（φ）；具体偏移量用窄区间算过，**修正后待复算**；ftrace 已直接证实清除在 IRQ 入口 ±6 µs | 实测 |
| ioctl 返回后置位比例为 0 | 43 个返回后样本 | 实测 |
| 窗口宽度与 `hw_elapse` 高相关 | corr(hw, width) = 0.997（窄区间算法；修正后待复算） | 实测（相关）/ 待复算 |
| ~~上升沿不是 kick~~ / ~~上升沿就是 kick~~ | **两条都已撤回**：只有区间关系（2.8~15.2 µs），kick 本身未测量 | 已撤回 |
| 上升沿随负载变化 | 8×8 k3 12.0 / 16×16 k3 14.5 / 32×32 k3 24.2 µs（各 6/6 BIT-EXACT）；现解释为**驱动 ioctl/调度延迟** | 实测（解释见 §1.2b） |
| 上升沿在 12–16 µs 窄带内，跨越 21× CNA 工作量 | 6 个点：12.1 / 12.5 / 16.0 / 14.9 / 13.1 / 16.3 µs；这是**软件侧提交延迟**的窄带，与 §1.2b 一致 | 实测 |
| 上升沿不跟作业时长、也不跟输出通道数走 | 只改 `oc` 的两组对照 rise 不变（11.7→12.0、14.8→16.0），hw 却 37.9→17.2、51.8→21.6 | 实测 |
| ~~上升沿与 CNA 工作量相关（0.970）~~ | **已撤回**：补齐 `ic` 轴（可达 21× CNA 工作量）后该相关降到 0.441，与 hw（0.551）、dpu（0.485）无差别 | 已撤回 |
| ~~上升沿 = "CNA 结束 / DPU 开始"~~ | 无证据支持 | 已撤回 |
| 上升沿**不随 NPU 频率成比例** | devfreq 受控扫描 300/500/1000 MHz：rise 15.75/13.71/13.20 µs；rise×freq 为 **4725 / 6854 / 13200 个周期**（约 4.7 千 ~ 13.2 千，**2.8×**） | 实测（n 小） |
| 上升沿语义 | ftrace 只给出"与调度入口的区间关系"，未定位到硬件动作 | **未识别** |
| 单 task 时组位与**提交序号奇偶**严格对应 | 105/105 无例外，跨进程成立 | 实测 |
| 多 task 时组位**不随 task 切换** | 2 task/提交恒 DPU_1，272 次连续运行中 DPU_0 出现 0 次 | 实测 |
| 组选择是 **job 级、写一次**，锁存自按 `task_number` 递增的计数 | 能解释全部观测 | **模型（未证实）** |

## 4. 已验证的负载（这是所有结论的前提）

**两档判据**（2026-10-21 新增第二档，实现见 `experiments/workload_verdict.py`）：

| 档位 | 条件 | 用法 |
|---|---|---|
| `bit-exact` | workload 打印 `RESULT: BIT-EXACT` | 默认档，本文绝大多数结论用它 |
| `ulp-bounded` | 失配比例 ≤ 5% **且** `max ulp ≤ 8` | 仅在 fp16 累加顺序导致差异时使用，**必须显式标注** |
| `rejected` | 其它 | 不得使用 |

第二档的由来：`--ic 32/48/64` 的形状与 CPU 参考只差 fp16 累加顺序
（如 31/1024 元素差 ≤4 ulp；`in=0x01 w=0x01` 在 fp16 下是次正规数，逐次累加顺序一变即不同）。
它**不是**橡皮章：`--ic 16` 的 45/1024、**max ulp 140** 就被判为 `rejected` 并排除。


| 负载 | 校验方式 | 结果 |
|---|---|---|
| `min_conv_exp --pattern --fp16`（多种尺寸） | 自身 CPU 模型比对 | **BIT-EXACT**，6/6 × 5 种配置 |
| `min_conv_exp --fp16 --iw 32 --ih 32` | 同上 | BIT-EXACT，6/6，中位 74 µs |
| `min_chain --tasks 2 --independent` | **不依赖模型**：两个输出逐字节相同 + 两者模型偏差相同 | PAIR BIT-EXACT 272/272 + 20/20（**仅该采集窗口内**）；该链后续**单独运行也会超时**，不能视为稳定探针。**注意**：两输出一致只证明"两次执行一致"，**不证明二者都算对** |
| ↳ 负对照 | `--tasks 1` | task1 缓冲未写 ⇒ 判失败（判据有效） |

**不通过校验的**：`min_conv --pattern`（全 MISMATCH）、`min_chain --tasks 2`（原版，
改为 `--independent` 后才通过）、`min_conv_exp --chain-id`（会挂 job）。

## 6. 目前能测什么、不能测什么

### 能（有板端数据支撑）

1. **单次运行内**解析一个状态的完整窗口 `clear→set→clear`：

   ```text
   wide/w01.csv  hw=77.9 µs
   ccccSSSSSSSSSSSSSSSSSSSSSSSSSccccc   32 个快照，跨度 84.6 µs
   ```

   命中率：`CAP=32` 时 **8/12**（复算一致：12 run、快照数中位 23、间隔 p50 2.625 / p90 6.416 µs、
   跨度中位 84.583 µs）。边沿按**读取区间**保守包围（例：`w01` 下降沿
   旧算法 `(81.958, 84.583]` → 修正后 `[82.541, 86.041]` µs）。
   窗口宽度下界 p50 **7.0 µs**；其中 1 个 run 两区间重叠 ⇒ 下界为负，说明**宽度不可分辨**，
   应按"无法排除更短"报告，而不是给一个正值。
2. 读出**作业在飞行位**（kick→IRQ 清除），并观测 `_0/_1` 与提交序号奇偶的对应（单 task）；
   但它是**整作业**粒度：未置位≠某块空闲，置位≠某块在算；组位关联≠已识别执行 bank；
3. 给出**调度路径入口与 IRQ handler 入口的实测时刻**（ftrace `mono_raw`：p50 15.9 / 124.1 µs，n=6）；
   `kick` 只有下界（≥15.9 µs），**块级完成时刻仍未建立**；
4. 给出 **submit→调度入口的实测值**（hook 入口后 13.2–33.0 µs，含 6.2–14.0 µs wrapper 开销），
   作为 kick 的**下界**；
5. 给出 ioctl 返回这一**同钟完成锚点**；
6. 判定工作负载是否正确执行（BIT-EXACT / PAIR BIT-EXACT / 显式 ulp-bounded）。

"**一句话**：已建立的是"**在部分已验证单 task 负载中，单次运行内能采到中断状态的
`clear→set→clear` 序列**"，以及它的**边沿区间**（区间宽度由相邻读取区间决定）。
**不是**"精确测得作业结束"，**不是**"模块忙闲测量"，更**不是**"某条命令在什么时候执行"。

### 不能

1. **任何 regcmd 位置**、task 内时刻或 per-regcmd 时长 —— 全部未建立；
2. 多 task 提交里的 task 级进度（组位不随 task 切换，且链不稳定）；
3. 模块级忙闲（`S_STATUS` 语义不可校验）；
4. **首个快照之前**窗口内的任何信息（该位置随配置变化：p50 5.98–11.67 µs，不是固定硬边界）；
5. 上升沿的物理含义已由 ftrace 解决（= kick）；但 commit 之前那 6.2–14.0 µs 的
   **wrapper 开销**尚未与真实驱动路径分离；
6. `--kw 1` 这类配置连数值校验都不过（0/6 BIT-EXACT），不能用来做对照；
7. ~~窗口起点语义不可用~~：已由 ftrace 定为 kick；窗口 = **kick → IRQ 清除**，
   粒度仍是**整作业**，不是命令或块。

## 8. 收尾判断与归档（2026-10-21）

### 8.1 这条用户态路线已经试尽的地方

| 尝试 | 结果 | 结论 |
|---|---|---|
| 模块状态字 `S_STATUS` | 可读、稳定，但不随负载变化，且无源码可校验语义 | **不可用** |
| 配置寄存器读回（自然标记） | 滞后一个 run，双 task 内 task1 完全不可见 | **不可用** |
| `S_POINTER` 判组 | 读回恒 0 | **不可用** |
| 人工标记写入（PPU/DPU 候选） | 输出无扰动，但**未取得有效窗口内的可见证据** | 暂停，未验证 |
| 中断状态位 | 单 task 下可用：置位窗口 = kick→IRQ 清除（ftrace 证实）；多 task 不随 task 切换 | **只能到作业粒度** |
| 上升沿 | 只有"与调度入口的区间关系"，语义未识别 | 不可用 |
| 清除沿 + `hw_elapse` | 高度相关，单次运行内可夹住（具体偏移待按读取区间复算） | **相关成立；"作业结束时刻"未建立** |

### 8.2 若还要继续，只剩下这些方向

1. **驱动侧（预期必须收紧）**：在 `rknpu_job` 的 commit / IRQ 路径打点，能补的是
   **软件事件**——`PC_OP_EN` 写入时刻、逐 job 身份、IRQ 入口与清位顺序、
   以及 **PM / job 生命周期保障**。
   它**不能**凭空给出 **bank、块级完成或 regcmd 进度**：这三者仍需要**可解释的硬件信号**。
   因此"换内核"只解决软件事件那一层，**不构成**获得 per-regcmd timing 的承诺。
2. **硬件 trace / 厂商工具**：不依赖用户态 MMIO 轮询的时间分辨率。
3. **换测量对象**：不用"当前哪条命令"，而用"整个作业的起止 + 组位"，做统计而非定位
   （现已具备的能力）。

### 8.3 不应再做的事

- 继续在用户态挖 `S_STATUS`/`S_POINTER`/配置寄存器（§8.1 已逐项排除）；
- 变换 2-task 链配置（交替即 80% 超时）；
- 用上升沿做任何定位或相位推断。
